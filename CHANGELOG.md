# Changelog

Harness is a fast, extensible, composable agent harness in Go. It ships a headless engine library, a CLI, and an HTTP+SSE server.

Harness is pre-1.0. The engine API, config schema, and plugin protocol may change between minor versions.

## v0.1.0 — Unreleased

First tagged release.

### Added

- **Engine library** (`engine`) — sessions are append-only logs of canonical messages. A session can change provider or model between turns with no history migration. Persisted sessions resume by ID.
- **Providers** (`provider/...`) — Anthropic Messages, OpenAI Responses, any OpenAI-compatible chat-completions endpoint (OpenRouter, Ollama, vLLM), and delegated turns through the Claude Code CLI.
- **CLI** (`cmd/harness`) — `harness run` for one-shot prompts, `-goal` for evaluator-checked goals, `harness serve` for the HTTP+SSE session API, and `harness sessions` to list saved sessions.
- **Tools** — built-in file and shell tools, custom Go tools through `engine.Config.Tools`, subagents through the `task` tool, and managed long-running processes (`process`).
- **Plugins** (`plugin`, `sdk/typescript`) — a language-neutral process protocol with a Go SDK and a TypeScript SDK.
- **MCP** (`mcp`, `mcpserver`) — an MCP client with deferred tool loading, and a Streamable HTTP MCP server.
- **Context management** — automatic and manual compaction, project `AGENTS.md` instructions, and [Agent Skills](https://agentskills.io/specification) (`skill`).
- **Deferred goals** — `POST /session/{id}/goal` accepts `defer: true` to arm a goal without posting its condition as a standalone turn. The loop starts after the next prompt turn and evaluates that turn first; on NOT MET the guidance turn carries the condition. `max_turns` caps the auto-armed loop, for deferred goals and for goals armed behind a busy prompt. A goal loop that spends `max_turns` without a MET verdict ends the goal: it journals `goal.cleared` with `goal_reason` `goal exhausted max_turns (N)` before `turn.end` with outcome `max_turns_exceeded`, and the session reads `idle`. On an idle session, updating an armed goal keeps it armed with the new condition and answers `armed`. A `max_turns` above 0 replaces the cap; omitted or 0 keeps it. Behind a busy prompt, the update answers `updated` and keeps `max_turns`. No evaluation runs until a turn finishes.
- **Context-window refresh** (`modelmeta`) — `go generate` rewrites the context-window tables from models.dev, and a daily workflow opens a pull request when they change. A new point release is recognized without a hand edit. Session creation still makes no network call.
- **Test model server** (`harnesstest`) — a scripted model server for tests in other modules. `New` speaks the Anthropic Messages wire; `NewChat` speaks the OpenAI chat-completions wire, with `Reply.Reasoning` and `Reply.ErrorCode`, and fails the test on a request that a real gateway rejects. Steps match requests in declaration order, `Block` steps wait for `Release`, `AwaitCanceled` observes a client that dropped a blocked request, replies can carry an error message and a `Retry-After` header, and the server fails the test on an unmatched request or a step that never matched.
- **Event-sink test receiver** (`harnesstest`) — `NewSinkReceiver` starts a scripted event-sink receiver that records every batch as a `SinkBatch`, answers each one through a `SinkReply`, and lets a test wait on the received batches with `Await`.
- **Session runtime core** (`harness`, `protocol`) — `harness.New` returns a `Runtime` that runs each session as one actor goroutine over a `Store`. `Create`, `Open`, `List`, and `Close` manage sessions; `Session` has `View`, `Submit` (idempotent by client input ID), `Interrupt`, `Events` (durable events after a seq, then live ones), and `Release`. An `Owner` grants each session; `Open` appends `owner.acquired` to fence earlier owners, ends a crashed turn, and resumes a turn that a handoff suspended. `OpenView` reads a session without owning it.
- **Session replication** (`harness`, `protocol`) — `Options.Sync` receives every record that a `Runtime` appends, in seq order, as a `protocol.SyncBatch`. A failed delivery resends the same batch; a `SyncAck` below the batch makes the sender resend from `Head+1` out of its `Store`. `ErrStaleEpoch` stops the session without another append. `Session.Release` and `Runtime.Close` return after the last record is acknowledged, and `Session.View` reports `SyncedSeq`. `ApplySync` implements the receiver rules over any `Store` for an embedder.
- **Codex backend** (`harness`) — `Options.Config` configures model providers, and the `provider/model` ref of `CreateSession` selects one. A `type: openai` provider runs turns on the OpenAI Responses API, the ChatGPT Codex lane included, over HTTP or the websocket transport. `Options.ModelTransport` supplies the HTTP transport of each provider, for each HTTP request and each websocket dial. The transport may supply the credentials, so the key variable may be unset. A model that no configured provider serves, or that `modelmeta` does not know, fails `Create` with `ErrModelUnavailable`; `context_window_required: false` or `context_window_tokens` allows an unknown model, and a ref with no provider fails with `ErrInvalidRequest`. A retryable model error, or a response with no text and no tool call, runs the turn again with backoff, up to `prompt_retries` times, when the turn has recorded no item. `Runtime.Close` closes the pooled websocket connections, also after a timed-out close. A reasoning item replays with its provider data. The model sees the session history from the newest compaction summary on.
- **Embedder tools** (`harness`, `protocol`) — `Options.Tools` takes `Tool` values that the model can call. After a model call that asks for tools, the turn runs each call in order, records its result, and calls the model again, until a call asks for no tool. A tool error, or a call to a tool that the session does not allow, is an error result that the model sees. `CreateSession.AllowedTools` restricts the tools that the model sees and may call; nil allows every tool. An interrupt stops a running tool, and the call gets an interrupted result. A handoff lets a running tool finish and starts no new tool. `ToolCall.ID` is the model's call ID.
- **Documentation** — package docs on pkg.go.dev, `engine` examples, and runnable programs in [`examples/`](examples).
- **Claude Code structured questions** — `harness serve -ask-user-question` lets a Claude Code session ask the user an `AskUserQuestion` question. The turn ends with outcome `awaiting_input` and a `question_call_id`, and `POST /session/{id}/question/{call_id}/answer` resumes it. Off by default.
